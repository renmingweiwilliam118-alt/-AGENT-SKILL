# RFlow Desktop / Shiflow Mini

The user's own desktop \"AI 工作站\" that **接待** (auto-replies) inside target windows: a 看 (capture screen/window) → 想 (LLM decides) → 做 (click/type/send) agent loop driven through a single-file web UI. Task class: product iteration (PM / UI / 3D+motion / feature passes) + agent-loop & capture & session/KB wiring + verifying the standalone window — to THIS user's standing spec.

## Always-on (project facts — trust, don't re-derive)

- Repo `C:\Users\mwr_w\shiflow-mini`. UI is ONE file `shiflow_mini/web/index.html` (HTML+CSS+JS, **no build step**), served live per request → a **window reload picks up UI edits, no restart** — but only because `/` sends `Cache-Control: no-cache`: WebView2 caches pages, so a restart can otherwise leave the window rendering the pre-fix page while every code check passes. Every UI change also bumps the visible build tag (AI WORKSPACE · v07xx in the brand block) so the user can confirm at a glance which build the window shows. `server.py` / `agent.py` / `native.py` / `capture.py` load at host start → **backend edits require a restart**. Venv `.venv\Scripts\python.exe` has all deps.
- **Primary interface = the standalone pywebview window (`python app.py`, 1440x920 + in-process backend on port 8765), NOT the browser console (`python main.py`).** Standing user rule: open/verify via the standalone window.
- **Security: `config.json` holds the user's LIVE OpenAI key.** It is de-tracked + gitignored; the live key exists ONLY in the local working copy. Never re-add `config.json` to git — a `git add -A` leaks it. Key reads come back masked (redacted placeholder), so never round-trip config.json through read→write_file — that persists the mask over the live key; edit it only with a targeted `patch` on the exact line. Tracked template is `config.example.json` (empty api_key).
- **Commits use the repo-local identity**: `git -c user.name="Maven Ren" -c user.email="mavenren@rflow.local" commit …` (not the global identity).
- The brain key in config is often a placeholder → 想 (`brain.decide`) fails while 看 (capture) works; that is config state, not a code bug. See `references/test-agent-loop.md` for driving the loop without a live model.
- **Standing preference: 全自动 only.** 辅助模式 (assist / manual confirm) and the pre-flight confirm gate are unwanted — the user runs this so replies are sent automatically. Auto mode must never block on a confirm gate; `open_session` forces `mode=MODE_AUTO`; the UI exposes only 「全自动」.
- **Minimal UI: no target-window preview panel.** `#targetBanner` div (the "目标窗口 · XXX" header) is REMOVED from index.html; `#shot` black preview element is `display:none` (JS that populates it still runs harmlessly). `#liveScreen` (桌面实时监控) has `overflow:visible` inline override because its `.col` parent clips tall images. The user's entry point is the **「🤖 自动监控微信」 button** (`autoWechat()` → `POST /api/auto/wechat`) — no manual region-pick, no window-list browsing. If re-enabling the preview later, restore `#shot` visibility and re-add the `targetBanner` div.
- **Auto-reception must read as visibly “on”.** A long-running auto process that shows nothing makes the user think it is dead (“点击了开始接待…不知道它在工作了”). Shipped affordances: `#watchBadge` — a small pill in the 看·想·做 panel header showing 🟢值守中 / 🟡运行中 / 🟡规划中 when the selected session’s status is watching/running/planning (hidden otherwise), updated from `openSession()`, the sidebar session-click, and the SSE `session`/`status` handlers. The watcher’s “开始值守：每 Ns 检查一次…” message only reaches the log panel because `handle()` switches on `p.type==='log'` → `log(p.text,'ok')` — add that case whenever you wire a new SSE event type that carries user-facing text. And a 409 from `POST /api/sessions/{sid}/run` while the watcher is already running is NOT an error: `runSession()`’s catch matches `/already running|planning/` and renders green “值守正在自动运行，无需手动启动” instead of the red “启动失败”. **Feedback at every stage of the 看·想·做 cycle**: the agent emits `log` events the user reads in the execution log: `🧠 正在思考，预计 10-30s...` (before the model call in `_think`), `✏️ 正在发送回复...` (before `type_text` in `_act`), `✓ 回复已发送：...` (after `send_ok` in `_act` via a `sent` event), and `✅ 接待完成（status=done），继续值守` (in `watcher._loop` after the agent run finishes). Without these, a 10–30 s model call looks like the system is dead. General rule: whenever you add process state that is invisible to the user, add a badge or log line so they can see it is working.
- **File→KB ingest is stdlib-only by design** (`parsing.py`: CJK decode chain, unzip OOXML, zlib pdf streams) — extend it in place, never add pypdf/python-docx/openpyxl; `python-multipart` (requirements.txt) is the one upload dep. Per-agent reply logic lives in `reply_rules` / `greeting` / `kb_doc_ids`. Surface map: `references/api-surface.md`.

## Verification (the user's hard gate)

Every deliverable must be **exercised, not described**: restart the standalone window after backend edits, confirm backend 200 on 8765 + live `msedgewebview2` child processes, and drive the running UI (or a fake-brain e2e for agent-loop logic) to observe the actual behavior before reporting. For UI CSS/JS, `node --check` the extracted `<script>` before delivery (per `html-js-syntax-gate`) **and count the `<div`/`</div>` + `<section`/`</section>` pairs** — an unbalanced tag is the usual silent break after an index.html patch and `node --check` will NOT catch HTML imbalance. A **UI-ONLY** change (index.html) needs just a WebView2 reload (Ctrl+F5 / re-navigate to 8765), NOT an app.py restart: the page is served per-request no-cache, so a reload picks it up. Reserve `Stop-Process`+`Start-Process app.py` for **backend** edits; over-restarting the backend for HTML-only churn re-binds port 8765 and wastes the user's time — he is cost-sensitive and will notice. Deterministic regression: `tests/test_reception.py`, `tests/test_lifecycle.py`, `tests/test_resume_learn.py` are **plain scripts, not pytest** — pytest is NOT installed in the venv; run each with `.venv\Scripts\python.exe tests/<file>.py` **directly** and expect `N/N passed` on stdout — they are bare `test_*` functions (NOT `unittest.TestCase`), so `python -m unittest discover` collects **0** and silently “passes”; running the file is what fires its `__main__` self-runner. `main.py --selftest` is the offline engineering suite (9/9, no window/model). The FULL project check is **`tests/run_all_e2e.py`** — one command that spawns an ISOLATED service instance (`RFLOW_DATA_DIR` tempdir) and runs all e2e scripts against fake windows; procedure, timing facts, and its idle-desktop requirement: `references/e2e-test-suite.md`. Always `py_compile` the backend modules you touched first — use `./.venv/Scripts/python.exe -W error::SyntaxWarning -m py_compile <files>` so a bad escape (notably a regex char-class that embeds a literal `"` inside a `"…"`-delimited raw string via `""` sequences, which is a `SyntaxError`, not just a warning) becomes a hard stop, then run the regression script, then restart + curl the API. (In a `"…"` raw string, put a literal `"` in the class as `\"` only; `""` terminates the string early.) Also: run compile/test/restart through the **`terminal` tool with the venv path directly** (MSYS `/c/Users/…` or `C:/…` forward-slash); `execute_code`'s `hermes_tools.terminal(command)` mangles backslash Windows paths (`C:\Users\x` → `C:Usersx`) so its `cd` silently fails — keep `execute_code` for reading/extracting, not for the shell steps. `tests/test_reception.py` uses small `FakeAgent`/`_StubSession` stand-ins, not the real `Agent` — add new deterministic checks there with that same pattern.

Live agent behavior is diagnosed from `/api/sessions` BEFORE touching code — trace entries carry `heard`/`reply`/`actions`/`model_ms`/`sent`(bool, True only when `_verify_sent` confirmed the screen changed after `press_enter`)/`verify`({ok,text,at} — set on the last trace entry after a successful send), the session carries `reply_count`(int, incremented by `s.reply_count += 1` in `_act` when `send_ok=True` — `0` means no confirmed send has landed yet), `last_verify{ok,text}`, and `last_replied`. A `trace[-1].sent=True` + `trace[-1].verify.ok=True` pair is the definitive proof a reply actually landed. `reply_count` counts lifetime successful sends. **Before calling it a code regression, confirm the environment:** 接待 stopping is usually that the chat app closed or the watched region got occluded, not the code. If a session targets a *desktop region* (title "Program Manager"), any window covering that region (dev tools, a browser, RFlow itself) makes the model correctly refuse to reply — the trace will say "没有聊天界面 / 代码编辑器 / 网页". Check `/api/windows` for a live 微信 window + `Get-Process WeChat` (empty = the chat app is gone; leftover `WeChatAppEx` are just mini-program helpers, not the chat). Reopen the chat app and bring it to the front on the monitored screen and it resumes — no code change needed. **Diagnosis shortcut:** if `reply_count=0` AND `last_verify=None` on a `status=done` session, the `press_enter` code path never reached line 756 of `agent.py` — the click/type/enter actions were silently skipped by the occlusion guard or focus-check, not a model failure. Check the SSE `warn` events for "无法把目标窗口提到前台" / "目标窗口无法获得焦点，已跳过写入". Run/verify paths are exercised harmlessly with a bogus hwnd (hwnd 999999: capture fails, nothing is typed into real windows). Pattern table: `references/verify-launch.md`.

## Liveness audit — 'is it actually 值守, and which features are dead?'

The user's recurring question ('现在还有哪些功能是无效的'). Don't guess — walk the whole chain against the LIVE system; each step is one cheap probe, stop at the first that's red and name it:

1. **Process alive?** `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8765/api/stats` → `200`.
2. **Heartbeat fresh?** `/api/stats` → `heartbeat.stale` false + small `age_s`; `last_crash` recent/absent.
3. **Actually watching?** `/api/sessions` non-empty + `/api/stats.totals.watching>0` + `data/heartbeat.json` `auto_watch>0`. Empty `/api/sessions` = the watch is NOT armed (see the terminal/`error`-session restore pitfall) — a 200 backend with zero sessions is 'alive but blind'.
4. **Resilience armed?** `rflow.py status`: 看门狗 跑着 + 8765 UP + all three keep-alive layers present (watchdog, `RFlow Watchdog` scheduled task, Startup `.vbs`); `data/duty.flag` present only in 无人值守 mode. All absent = a crash/reboot leaves it down and it will NOT come back.
5. **Capture not frozen?** `data/crash.log` tail for '画面冻结 Ns' and read the `mode=` in the line: under the standing `pin_wechat=false` (dc) mode an occluded-but-open WeChat is NORMAL and quiet-chat frames are naturally static — only a dc freeze past the ~600 s dc threshold (or WeChat minimized) is blindness. Under `pin_wechat=True`, occlusion/not-foregrounded = silently blind for that window (messages missed).
6. **No duplicates?** Count processes by `CommandLine` role (run_forever / app.py / pmcap), NOT by the parent-tree (PID reuse makes it look self-nesting). Count with `@(x).Count` — `@(x | Measure-Object).Count` always returns 1 (@() collects the pipeline's single result object, not the items measured), hiding both duplicates and absence behind a false all-clear. Two live `app.py` on the same WeChat hwnd = double replies to the customer — **but distinguish the normal launcher-stub pair first: the venv python stub re-exec the real interpreter, so ONE launch shows a parent+child pair sharing the same CommandLine (also true for `run_forever`); that is a single instance (the App named-mutex would have exited a true second one). The danger is INDEPENDENT trees (different roots), not one stub+real pair.**

Report each RED step as the 'ineffective feature' with the exact probe output that proves it — the user wants root-cause + a one-shot fix, not a symptom list.

## Pitfalls that cost real time

- **Adding a new view/control to index.html is a slice, and every control MUST bind a live backend endpoint (the user's hard “no fake UI” constraint).** Ship no static demo control that has no real API behind it. Before reading `d.X` in the UI, grep the backend handler’s ACTUAL return-dict keys — a wrong key reads `undefined` and the control silently renders nothing (this project’s `/api/model/test` returns `{ok, message}`, not `{detail}`; reading `d.detail` showed a blank). Reuse existing endpoints wherever a feature can (top-bar 全局搜索/通知中心 are pure-frontend over `/api/customers` · `/api/receptions` · `/api/kb/search` · `/api/lifecycle/control`). If the endpoint does not exist yet, mark the feature P3 and defer it rather than fake the UI — the deeper work is backend first, THEN the UI. The three P3 governance items are now SHIPPED (so they are NOT "defer" anymore): 片段级管理 → `kb.list_chunks`/`set_chunk_weight`/`remove_chunk`/`merge_chunks` + `POST /api/kb/chunk`; 高风险动作授权 → `Agent._high_risk` + `POST /api/reception/risk` (config `reception.high_risk_patterns`, NOT an `AgentIn` field — the gate is global); 主/备模型 → `config["brain"]["fallback"]` + `ModelIn.fallback` (FailoverBrain). Full shapes in `references/api-surface.md` § P3. Verify each bound endpoint with one live curl/python call before reporting the feature works.
- **A P1/P2 reliability + business layer now lives in `message_lifecycle.py`** (ReceptionStore / ControlState / CustomerStore, wired into `watcher.py` + `/api/lifecycle/*` + `/api/customers` in server.py). Two invariants keep the two worst bugs away: lock a dedup/ACK fingerprint **only** on a `_verify_sent`-confirmed send (else "回两句就哑"), and gate **every** send path (main trigger + periodic `_kick_unanswered` re-kick + retry) behind `ControlState.send_allowed` (else 急停 doesn't 真停). A third invariant of the same family: **append an assistant reply to `s.turns` ONLY on `send_ok`** — a failed reply left in history makes the `_is_dup_reply` last-4 guard judge the retry's identical (correct) answer as a duplicate and suppress it, so that customer line is NEVER answered; pair it with skipping the dup-reply interception entirely while `s._unanswered_msg` is set (the bounded-retry path owns that line). `get_store/get_control/get_customers` cache singletons by base-dir → **deleting a backing JSON does NOT reset the running process (restart to reset; unit-test the stores against `tempfile.mkdtemp()`)**. Full map: `references/reliability-lifecycle.md`.
- **Two divergent session data models coexist in index.html.** The LIVE ones are `renderSessions` / `openSession` using the `sessions` global + `s.id` / `s.window_title`; an older `sessionList` / `s.sid` / `card()` / `refreshSessions` shape lingers in stale reads and is not the real code. **Grep the live symbol definition before editing**, and re-search after every edit — this ~1450-line file shifts line numbers on every patch, and a stale read will steer you to the wrong model.
- **In the `.map(s=>{…})` card renderers (接待台 `renderReceptionDeck`, `renderSessions`), build multi-branch button/segment strings with `let x=''; if/else` — never a nested-ternary concatenation.** `const btns = pend ? A+B : (st==='p' ? X : Y + (st==='r' ? Z : ''))` is one `)` short the moment you edit it, and `node --check` does NOT report the broken ternary: it loses sync and reports `Invalid or unexpected token` dozens of lines later (at an unrelated `const tok=…` / `catch`), so you chase the wrong line. Verify any JS edit of index.html by `node --check`-ing the extracted `<script>`; when a template-literal block fails, extract just that `.map` body and test it in isolation with stubbed globals — the ternary is the usual culprit. Same trap: wrapping an `if(c){…}` body in braces inside `try{ … }catch` silently eats the try's closing `}` — add the extra `}`.
- **Confirm-vs-abort gate race.** A pre-action gate that blocks on one `threading.Event` and can be released by MORE THAN ONE caller (a confirm AND an abort/close) must, on wake, re-check the abort flag before treating the wake as \"confirmed\" — otherwise a cancelled plan is indistinguishable from an approved one. Keep unblock-by-abort **and** the post-wake re-check. `references/test-agent-loop.md`.
- **Helper names & the brain/capture API drift from a fresh session's guess — grep the live symbol before coding, never reconstruct from memory.** The run entry is `runSession()` (auto-opens a session for `selWin`, then POSTs `/api/sessions/{cur}/run`), **not** `startRun()`; `openSession()` builds from `selWin` and forces `mode='auto'` + `skip_gate=true` (辅助模式 removed). `capture` exposes `grab_window(hwnd, max_width, prefer_screen)` / `grab_rect(rect, max_width)` / `grab_desktop(max_width)` / `region(img, rect)` — there is **no** `grab_desktop_region` or `build_desktop_payload`. `brain.decide(img, ctx) -> Decision`; `Decision` fields are `intent/reasoning/reply/heard/confidence/needs_human/actions/stop/tokens` (+ `.to_dict()`; `tokens` = this call's token cost, set in each vision brain's `decide` from the provider `usage`), **not** `action`/`reason`. Full trust-don't-re-derive map: `references/api-surface.md`.
- **Use the real CSS tokens; an undefined `var()` is silently dropped, not an error.** `:root` defines `--border --border-2 --panel --panel-2 --success --error --accent --accent-soft --grad --text --text-2 --text-3 --bg`. `--hair`, `--good`, `--card`, `--card-2` are **not** defined — `border:1px solid var(--hair)` compiles but the border never renders. Tint a surface with `color-mix(in srgb, var(--success) 14%, transparent)`.
- **Launch window detached with `pythonw.exe` — every link of the supervision chain MUST be GUI-subsystem, or the user gets black cmd boxes on his desktop.** A tool `background=true` job (even `persist_on_release`) is reaped on session turnover → the window closes, 8765 stops answering. Two mechanisms create visible consoles when a link is `python.exe` (console subsystem): the Task-Scheduler task allocates a fresh console on every fire (an every-minute task = a per-minute flash), and a console-less parent (run_forever runs DETACHED) Popen-ing a console-subsystem child gets a NEW console per respawn — `-WindowStyle Hidden` hides only the direct child, never grandchildren or task fires. Hermes-launched instances: `powershell -NoProfile -Command "Start-Process -FilePath '<repo>/.venv/Scripts/pythonw.exe' -ArgumentList 'app.py' -WorkingDirectory '<repo>'"`. Shipped: ALL supervision links run `pythonw.exe` — `rflow._ensure_cmd()` (task + Startup `.vbs`), `rflow.py duty on`'s watchdog launch, `run_forever.CHILD`, `ensure_watchdog`'s Popen — verified (task fires clean, whole chain pythonw, 8765 200, live receptions). After changing `_ensure_cmd()`, re-register the task (`install` / `duty on`) or the OLD `python.exe` command line keeps firing with boxes. pythonw has no console → a dead one leaves no stderr: diagnose via `data/crash.log` + port 8765, don't relaunch blindly. `kill_app.ps1` matches both exes. Re-check `/api/kb` → 200 before blaming code. `references/verify-launch.md`.
- **A window that looks 'cut in half' is usually the capture, not the CSS — but can also be the target app's own empty state.** PrintWindow on GPU/DirectUI windows can half-paint, or return a rect-sized frame with the real content offset inside it; `_is_blank` alone lets that through. Validate with `_looks_cropped`, reject the candidate, and use `grab_window(hwnd)` (PrintWindow first — occlusion-proof; `_usable()` rejects half-painted GPU frames → auto-falls back to screen pixels when window is visible). **Never use raw `grab_rect(rect)` for model/watcher/baseline captures** — GDI BitBlt grabs whatever is VISIBLE at the screen coords → grabs RFlow's pixels when RFlow covers WeChat → model reads RFlow UI instead of WeChat content (symptom: '截图模糊/无聊天内容'). **Triage BOTH ways before touching CSS** — a preview that 'misses the chat body' can be the TARGET's own state: WeChat with no conversation open = contact list + empty pane; sessions then stall `paused` at `reply_count=0` because the model correctly refuses to act with no input box. The user will report '窗口显示不全' when the preview faithfully shows a contact-list-only WeChat. Order: (1) capture file on disk → check size matches `native.get_rect(hwnd)` → verify bottom band brightness (dark=no input box); (2) VL-describe what the target actually shows — if it says '联系人列表,没有聊天窗口', the capture is complete and the issue is the target, not the code; (3) only then touch the preview CSS. Recipe: `references/verify-launch.md`
- **Overlay boxes must map in pixels, not percentages.** A `%`-of-wrapper pick box drifts the moment the preview is not the wrapper's full size — compute from `img.getBoundingClientRect()` (see `renderShotPick`).
- **Verify a click target read-only (no cursor move, no message sent).** To check where a click would land without disturbing the live session: `r = native.get_rect(hwnd)` → `px = r[0] + ix*(r[2]-r[0])/img_w`, `py = r[1] + iy*(r[3]-r[1])/img_h` for a representative image-space point → `native.top_level(native.window_at(px,py))`. `window_at` is `WindowFromPoint` (read-only — it does not move the cursor). Caveat: in a standalone probe the *top* window at that point may be RFlow's own pywebview window or another visible app, not the target; that is EXPECTED, not proof the click will miss — the agent's real click lands on the target only because `_act` first does `window_minimize(self._own_hwnd)` + `bring_to_front(hwnd)`. So a read-only probe returning a different top-level hwnd tells you the geometry (is the point inside the window bounds?) but NOT that the click will be occluded.

- **GDI virtual-screen capture includes the capturing app's own window.** `capture.grab_desktop()` (GDI BitBlt of the virtual screen) captures pixels, not the z-order — when RFlow is in the foreground, the capture shows RFlow's own UI, not the desktop behind it (symptom: "桌面不完全" / WeChat not visible in 桌面实时监控). Fix: `GET /api/screen?minimize=1` minimizes the RFlow pywebview window (`agent._own_hwnd`, set via `agent.set_own_hwnd()`) for 0.25 s before the GDI capture, then restores it. The 桌面实时监控 tick function passes `minimize=1` on every poll. For the agent-loop's own `grab_window` captures this is already handled by `_act`'s minimize-restore (see `just_clicked` pitfall above) — the desktop-monitor capture is the second place that needed the same fix.
- **Capture integrity: run `native.ensure_front(hwnd)` before EVERY `prefer_screen` capture of a target window, and fall back to DC capture when it can't be foregrounded.** `prefer_screen` grabs whatever pixels are on TOP of the screen rect, so a RFlow/terminal/editor covering WeChat makes the agent/watcher silently capture the *wrong app* and the model then "correctly" refuses to reply — the #1 "no reply / 没回答" cause is a capture bug, not the model or the prompt. `native.ensure_front` = `bring_to_front(hwnd)` + verify the window is still the top-level at its center (`window_at→top_level == hwnd`): True → foreground, use `prefer_screen=True` (fresh pixels); False → fullscreen on top / stale hwnd, use `prefer_screen=False` (a DC/PrintWindow of the window body — still the right content, just possibly a stale frame). Both `agent._think` (the model's input frame) and `watcher.snapshot` (the trigger/baseline frame) now do `front = native.ensure_front(s.hwnd)` → `grab_window(s.hwnd, …, prefer_screen=front)`. **The watcher must re-assert this on EVERY poll, not only in `start()`:** the user/RFlow/terminal steals foreground between polls and each stolen poll both captures the occluder AND poisons the baseline with a wrong-app frame, so later diffs compare wrong-app vs wrong-app and miss real messages. - **Run/stop RFlow via `rflow.py`, not a hand `Start-Process`.** `run_forever.py` is the process-level watchdog (survives 0xC0000005 segfaults that kill 8765, auto-relaunches `app.py`, logs to `data/crash.log`). **Supervise the backend by a real-PID file + port, never by the Popen handle:** the venv `.venv\Scripts\python.exe` is a ~250 KB launcher stub that re-execs into the real interpreter, so a `Popen(python.exe, …)` handle dies instantly; a naive watchdog sees 'child dead' and respawns every few seconds → a stack of launcher+child each grabbing 8765 → the classic '半天不回 / 窗口没了' restart storm. The same stub makes `subprocess.run(..., timeout=N)` LEAK: the timeout kill touches only the stub while the real grandchild (the actual worker, e.g. `pmcap.py`) goes orphaned and accumulates one zombie per timeout — tree-kill with `taskkill /F /T /PID` on timeout AND non-zero exit, spawn via `Popen` + bounded `p.wait(timeout≈12)` behind a serializing lock, and sweep stale instances by command-line match at service startup (the `_PMCAP_LOCK`/`_kill_tree`/`_sweep_stale_pmcap` pattern in `server.py`). `app.py` writes its true `os.getpid()` to `data/app.pid` after taking the single-instance mutex; the watchdog judges liveness by `pid_alive(data/app.pid)` AND port 8765, restarting only when the real backend is actually down. Do NOT 'simplify' this back to Popen-handle monitoring. single-instance is enforced by a **Windows named mutex, not lock files** — `shiflow_mini/single_instance.py::ensure_single_instance(key, repo)` (`CreateMutexW`, name = `Local\RFlow-<key>-<sha1(repo)[:8]>`): `run_forever.py` takes key `"Watchdog"`, `app.py` takes key `"App"`. A named mutex is **system-managed and auto-released the instant the holder dies** → no stale file, no TOCTOU race. This REPLACED the old O_EXCL `data/watchdog.lock` / `data/single_instance.lock` + live-pid + stale-takeover scheme: that scheme left a stale lock whenever a holder segfaulted or was force-killed, so a later launch mis-took-over and stacked → multiple watchdogs each relaunching `app.py`. Any 2nd top-level launch now finds the mutex already held → logs '另一个看门狗已在值守（命名互斥锁）' and exits. **Process-tree diagnostic:** `Get-CimInstance Win32_Process -Filter "Name='python.exe'"` and read `CommandLine`+`ParentProcessId`+`CreationDate` — a **quoted** python path = shell/`Start-Process`-launched, an **unquoted** path = `subprocess.Popen`-launched. **Distinguish the LIVE app from idle leftovers by (has the RFlow main window) AND (owns port 8765, `Get-NetTCPConnection -LocalPort 8765`) AND (many threads)** — a 1-thread / no-window / no-port leftover is not the app (a raw `Start-Process` launch can leave one behind). A child can share its parent's job object, so `Stop-Process` on the "extra" PID can take the live app down: read `ParentProcessId` first and, when in doubt, leave the idle one alone rather than risk the running watcher. A `Start-Process`-launched watchdog can still self-stack `wf→wf→app→app` from a launcher/shim layer *outside* the repo (the .py sources contain NO `run_forever.py` launch string) — the mutex only stops *repeated top-level* starts, so always launch via `rflow.py start` (one detached watchdog), never hand `Start-Process`. **Root cause of the classic '半天不回复 / 窗口没了':** two competing `run_forever.py` watchdogs each hold a port and keep relaunching → a restart-storm of `app.py 退出 rc=0 (存活 5s) → 自动重启` every ~30 s in crash.log. Ops: `python rflow.py stop` (kills the whole tree: `*shiflow-mini*` / `*run_forever.py*` / `*app.py*`), `python rflow.py start` (one detached watchdog), `python rflow.py status` / `rflow.py log` (health + crash.log). **No `rflow.py restart` subcommand** — to apply backend edits, `stop` then `start` (or `stop` then `duty on`). **`duty on` / `duty off` are the high-level toggles**: `duty on` = install + enable the self-heal stack (watchdog + Task-Scheduler `ensure_watchdog.py` + Startup `.vbs`) and launch, i.e. 无人值守/自动复活 mode (crash/kill/reboot → ≤1 min auto-respawn); `duty off` back to 普通模式 (关掉就关). **Order rule when arming duty around a restart:** the app reads `duty.flag` ONCE at startup (`_restore_checkpoint` trusts ONLY the flag — present → re-arm; absent → force `auto_watch=False`), so an app launched BEFORE `duty on` restores idle and STAYS idle even after the flag later appears; after `duty on` against a running idle app, bounce `app.py` once (kill it — `run_forever` respawns in ~5 s) so the reload restores with the flag present. Never assume the watch armed: verify `data/heartbeat.json` `auto_watch>0`. Confirm the mode with `rflow.py status` (看门狗: 跑着 / 没跑 + 8765 UP + heartbeat). Never launch with bare `background=true` (reaped) or a hand `Start-Process` (orphan stacks). Full recipe: `references/verify-launch.md`.
- **"It keeps running / survives a reboot" = three OS-level layers, not one Python watchdog.** A lone `run_forever.py` does NOT survive its own crash or a machine reboot, so the user's standing spec (multi-hour unattended 接待 that "never silently dies") needs the two system layers on top of it: ① `run_forever.py` respawns `app.py` in seconds (existing); ② a **Windows Task Scheduler** task `RFlow Watchdog` (`schtasks … /SC MINUTE /MO 3`) that runs `ensure_watchdog.py` — which **probes whether the watchdog is alive via the `single_instance` named mutex — `OpenMutexW(SYNCHRONIZE=0x1, …,"Local\\RFlow-Watchdog-…")` = existence test. **The access right must be non-zero:** `access=0` makes `OpenMutexW` return `ERROR_ACCESS_DENIED(5)`, so a live watchdog reads as dead and every task fire re-spawns a 2nd watchdog/app — the count climbs a pair per cycle instead of no-op-ing (see the `OpenMutexW(access=0)` pitfall in `windows-process-inspection`). If dead, relaunches `run_forever.py` **fully detached** (`DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP`); idempotent, so the fire is a no-op when healthy; ③ a **Startup-folder `.vbs`** under `shell:startup` (`%APPDATA%\…\Start Menu\Programs\Startup\`) that runs the same `ensure_watchdog.py` at logon for instant reboot recovery. `ensure_watchdog.py` self-locates the repo + venv from `__file__`, so it is cwd-independent and works on any machine once registered. Manage all of it with **`python rflow.py install` / `uninstall`** (creates/deletes the task + the .vbs). Prove it before reporting: kill the whole process tree → confirm 8765 down → run `ensure_watchdog.py` → confirm 8765 is back within ~15 s.
- **An un-killable guard needs a symmetric off-switch, or the user can never turn RFlow off ("关不掉 / 关掉后还会再出现").** The three keep-alive layers make RFlow un-killable by the *system* — but with no off-switch, killing the processes just triggers the next task fire → respawn. `rflow.py` now ships both directions: **`stop`** = write the sentinel `data/stop.flag` + `schtasks /Change /Disable /TN "RFlow Watchdog"` + kill the whole tree (disable the task *before* the kill so a fire can't race it); **`start`** = clear `stop.flag` + `schtasks /Change /Enable` + launch one detached watchdog. `ensure_watchdog.py` AND the Startup `.vbs` target check `stop.flag` FIRST and no-op if it exists — so even a reboot/login respects the stop. The kill-all filter must exclude the manager CLI itself (`-notlike '*rflow.py*'`) or `stop` self-kills before printing its confirmation. A successful `stop` = 0 processes + task disabled + `stop.flag` present, and it stays off.
- **Closing the standalone window = a complete stop, not a respawn (the GUI-side off-switch).** `app.py` now runs `complete_shutdown()` the instant the pywebview window closes (`webview.start()` returns). The current design plugs three historical leaks at once — a per-minute spurious revival from a dead `ensure_watchdog` liveness probe, `run_forever` respawning with no flag check, and the closer process dying mid-kill-loop so every step ordered after the loop never ran. Rules: **write `data/closing.flag` in the FIRST millisecond** — every revival path (`ensure_watchdog`, `run_forever` at startup and per probe tick, the supervisor's duty-flag self-heal) checks it before anything else and exits, so the shutdown can take arbitrarily long without a race; stop the supervisor + clear all `auto_watch`; delete `duty.flag` + clear `app.pid` + disable both tasks all BEFORE the kill loop (leftover duty.flag after a close = the closer died before cleanup, not a watchdog leak); the PowerShell kill loop LAST (it is parent-independent and finishes even if the closer dies). `rflow.py duty off` writes `closing.flag` first too; **`duty on` DELETES `closing.flag`** — that re-arms revival semantics. `watchdog_alive()` must probe BOTH `_mutex_names` entries (a LIST — the singular `_mutex_name` does not exist) with a run_forever process-count fallback; a probe that can die inside `except: return False` reads 'dead' on EVERY task fire and revives every minute (the per-minute '另一个看门狗已值守' log wall). Full order + the WM_CLOSE shutdown E2E (real close path, T+12/35/95 s sampling, manual task-fire test): `references/verify-launch.md`. Net semantic: a deliberate close stays closed; only a genuine crash / segfault / external kill should auto-respawn. This is the window-close counterpart to `rflow.py stop` (CLI) and is what finally answers '关不掉 / 关掉后还会再出现.' Because `complete_shutdown` lives in `app.py` (a backend edit), the LIVE process serving 8765 is the pre-fix build until it is relaunched — restart after landing it. Verify the close end-to-end: close the window → `Get-CimInstance Win32_Process` for `shiflow-mini`/`run_forever.py`/`app.py` (minus the CLI) reads 0, 8765 drops, and 60 s later nothing has come back.
- **On this user's box, register the task with `schtasks`, NOT PowerShell `Register-ScheduledTask`.** `Register-ScheduledTask`'s repeating-trigger DateTime binding throws `PositionalParameterNotFound` ("positional parameter … not in correct format") on a CJK-locale machine — `schtasks /Create /TN … /TR … /SC MINUTE /MO 3` works natively. A **repeating** task (`/SC MINUTE`) is creatable **without admin**; `/SC ONSTART` and `/SC ONLOGON` are **admin-only** (a normal user gets `拒绝访问`/access-denied) — hence the Startup-folder `.vbs` for non-admin reboot recovery. `schtasks` emits **GBK(cp936)** text: judge success by `returncode==0`, never by grepping the Chinese output; decode bytes via `cp936` only if you must display them. Keep the task/`.vbs` command line a bare `<venv-python> <repo>\ensure_watchdog.py` (add inner quotes only if the path has spaces). Recipe: `references/verify-launch.md` § Unattended self-heal.
- **No conversation open → open it before you can even find an input box.** On the WeChat MAIN window with no chat open, the right pane is empty (two grey bubble placeholders), there is **no input box**, and a new incoming message only adds a red dot in the LEFT list. The model then emits a `click` on that left-list row to open the conversation — but `_robust_send`'s "drop the click when the sequence has `type_text`" rule **swallows that open-click** → nothing ever gains focus → the reply fails (symptom: '收到新消息时不能点击并回复'). Fix in `_act`: discriminate the click by position — **bottom-right** (`x≥0.30·W` AND `y≥0.75·H`) = focus-the-input → keep the robust-send no-click/sweep path (pre-opened-chat behavior unchanged); **left-list / upper** click = open-the-conversation → do a REAL click, then `sleep 0.4 s` for the input box to render, then type+enter. The x-fence is 0.30, NOT 0.40: WeChat's contact list ends below ~0.28·W, and the model's input-box click frequently lands at the input's LEFT edge (~0.39·W) — a 0.40 fence misreads that as an open-conversation click, the bare click lands nowhere, and the type/enter chain retries the same dead send for all ~12 steps. Same reasoning pushed y to 0.75. Teach it in the vision prompt: 'if the right side has NO input box, first click the unread row in the left list to open the chat, then type.' Backward compatible: a pre-opened single chat (input box visible) still just uses robust-send.
- **A message from a NEW or non-open contact needs THREE aligned layers — trigger, prompt, and dedup-gate — miss any ONE and it is silently never answered.** (1) *Trigger*: the left-list strip watch (rule in the trigger section; `references/multi-contact-reception.md`). (2) *Prompt*: the vision prompt FIRST instruction is scan the left list for unread badges; a badge on a row OTHER than the open conversation ⇒ this round emits ONLY `click` that row + `wait ~1 s` with `heard`/`reply` null (never guess a reply from the row preview — the NEXT round reads the real message and answers); multiple unread → click the topmost; skip non-human rows — by SHAPE, not name list: any article-push-style preview (【公号名】标题 / 标题+摘要 / 图文卡片) = 公众号/官方号, NEVER click (微信游戏 was off the old name list; clicking strands the watch in a feed) — and a right pane already showing a feed/game page (no bubbles, no input box) → `reply=null`, no actions, `stop=true`; a friend-request panel (接受/拒绝 buttons, no input box) → click 接受 first. (3) *Gate*: the `no_new_msg` screen-diff gate must strip ONLY send actions (`type_text`/`press_enter`) and PRESERVE `click`/`wait` — the sidebar badge is ~2 % of the message band, so the gate fires no-new-message exactly when the model correct decision was to OPEN the unread conversation; wiping the whole action list erases that click and the contact is never opened. Symptom per missing layer: never fires (rx flat) / fires but stares at the open conversation (heard+reply null every round) / model decides correctly but the click is silently erased.
- **Closing the last 'silently missed a message' gap = the content/freshness/alarm layer on top of the two-stage trigger (the A+B+C pattern).** The two-stage trigger only fires when pixels CHANGE, so it still *silently* misses: (a) a message whose pixel delta is below threshold or got absorbed into the baseline; (b) a capture that went stale because WeChat couldn't be foregrounded; (c) a frozen/occluded window whose capture never changes. Cure each without claiming literal 100% (pixels+OCR can't guarantee it, but they can stop being *silent*): **A stable-screen OCR backstop** — on a *stable* poll (diff<threshold), every `stable_ocr_scan` (~10 s) re-OCR the last customer bubble via `brain.triage` and, if its md5 ≠ `s._last_new_hash`, run reception (catches below-threshold/absorbed; keep it conservative — only `new=True` triggers, and throttle it or you burn the LLM every 0.5 s); **B observable capture freshness** — record each capture's mode (`screen`=fresh foreground vs `dc`=occluded stale-frame fallback from `ensure_front` returning False) and throttle-warn when it fell back to DC; **C frozen-capture alarm** — keep a cheap per-frame signature (md5 of a ~48×30 grayscale downsample) and alarm + write `crash.log` when the message region stays byte-frozen — **the threshold MUST branch on capture mode: ~45 s (`screen`) vs ~600 s (`dc`)**. The "a live WeChat always has cursor/clock/typing-dot motion" premise only holds for SCREEN captures; a dc (PrintWindow background) frame of an occluded, quiet chat is naturally byte-static, so a flat 45 s under dc fired a false 画面冻结 alarm every ~60 s (90× in one duty run). Branch the REPEAT-alarm interval too (60 s `screen` / 600 s `dc`), or a legitimately-quiet dc watch re-alarms every minute and floods `crash.log` even after the threshold is raised. A dc freeze past minutes = truly dead capture (e.g. WeChat minimized). Refactor so the pixel-change branch and the stable-OCR backstop share ONE settlement path (gate → bounded retry → settle/record, `message_lifecycle` store) so their behavior can't drift. **Concretely, the stable-OCR backstop must SKIP whenever `_unanswered_msg` is already set — the bounded-retry path owns that message and drives the `_unanswered_kicks` counter; if the OCR path resets that counter on its own per-failure, `unanswered_max` is defeated and you get an unbounded `rx_count`/`fail_count` run (the 'keeps re-thinking the same line / 越收越多越卡' symptom).** On `unanswered_max` exhaustion, clear `_unanswered_msg` BUT lock that line's text-hash so that specific message can't re-trigger. Add a deterministic fake-brain regression for A and C. State the honest ceiling to the user: even A+B+C is 'practically ~100%, not literal' — the only literal-100% path is a **message-level hook** (WeChatFerry / UI-Automation reading the incoming-message *event*, not pixels), which is WeChat-version-fragile; offer it as a separate decision.
- **After a restart, a *terminal* (`done`) session is NOT restored to a live watcher — so '又看不到新消息了' is usually 'the watch simply isn't armed', not a detection bug.** `agent`'s checkpoint-restore skips terminal sessions, so `/api/sessions` comes back empty and `data/heartbeat.json` shows `auto_watch:0` = nothing is polling. Diagnose in that order and stop: read `heartbeat.json` (`auto_watch` count) + `/api/sessions` to confirm a watcher is actually running BEFORE touching pixel/triage logic. Re-arm with `POST /api/sessions {hwnd, mode:"auto"}` — the handler auto-starts the watcher AND runs the current screen once (so a message already on screen gets answered, not just future ones); confirm `hwnd` is still alive first (`native.is_window`). **On this startup path a *non-terminal* (active/paused/running) session now auto-restores: `Agent.__init__` calls `_restore_checkpoint()`, which loads the checkpoint's active session into `sessions` as `paused` and sets `pending_resume_sid` — so only a *terminal* session needs the manual re-POST. **`error` is terminal too:** `write_checkpoint` writes `active = s.status not in _TERMINAL`, and `error` is in `_TERMINAL`, so a watch that dies in `error` (frozen/occluded capture, crash mid-watch) is persisted with `active:False` → `_restore_checkpoint` skips it → it never reaches `agent.sessions` → the supervisor (which re-arms only sessions already in `agent.sessions`) has nothing to re-arm → the unattended watch silently dies and **stays dead across the restart**, defeating the 'never silently dies' spec. In 无人值守/duty mode treat a *non-user-aborted* `error` session as resumable (restore + re-arm it as `paused`/`watching`); only a user-initiated `done`/abort should be dropped. **The durable on/off signal is `data/duty.flag`, NOT the checkpoint's `active`/`duty` fields:** `watcher.start` writes it, `unwatch` deletes it, and `rflow.py duty on` installs it (+ the scheduled task). A checkpoint can be saved while the session is already `done`/`active:false` (the watch just finished a round), so `_restore_checkpoint` must re-arm when `duty.flag` exists EVEN IF the snapshot looks terminal — read the flag and force `is_duty`/`auto_watch=True`; trusting the snapshot's `duty` field alone makes every restart silently kill the unattended watch (symptom: `/api/sessions` empty + `watching:0` right after a respawn despite duty mode 'on'). Tell: checkpoint `session.status=='error'` + `active:False` + empty `/api/sessions` + `heartbeat.auto_watch:0` = a watch that should be running but is dead. Verify that call-site still exists whenever you touch the checkpoint path: a `_restore_checkpoint` that is defined but never invoked silently leaves `sessions`/`pending_resume_sid` empty (a fresh-object resume test fails on its first assert), and no unit test catches a missing call-site that a runtime one does.
- **git-bash mangles CJK inside `curl -d` JSON bodies** (`-d '{"title":"微信"}'` → non-UTF8 bytes → FastAPI `{"detail":"There was an error parsing the body"}`). The `title` field on `POST /api/sessions` is *optional* (defaults to `hwnd <n>`), so for probing just omit it; when a real title is needed, write the JSON to a UTF-8 file and `curl -d @file`.
- **A redundant in-function `import X` makes `X` function-local even when a module-level `import X` exists** → `UnboundLocalError` at any *other* call-site in the same function that reads `X` before that local binding runs (hit by adding a module-level `import hashlib` while the pixel branch still had a local `import hashlib`; the stable-screen branch, which runs earlier in the loop, blew up on `hashlib.md5` and silently killed the watch thread). When you add a module-level import, delete the now-redundant in-function imports, then compile AND run the branch that executes *before* the local import.
- **After a non-exact (fuzzy / `block_anchor`) patch, re-read the rewritten region and confirm each identifier resolves in that scope — `py_compile`/pyflakes will NOT catch a wrong `self.<attr>` or an undefined local.** The AST has no name analysis for attribute access on a bare `self` and no symbol table for locals, so it accepts `self.agent._emit(sid, …)` when the method's real members are `self._emit` and the local is `s.id` (copied from a different context). Editing `agent._think` I wrote `self.agent._emit(sid, …)` instead of `self._emit(s.id, …)`; compile passed and only a `grep` for the symbol + re-read caught it before restart. Rule: after any patch that rewrites a block, `grep` each identifier you introduced and confirm it exists in that method (`self.X` = an Agent attribute; `sid` vs `s.id`).
