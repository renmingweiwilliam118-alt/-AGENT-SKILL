# Targeting & capturing the WeChat window (Win32 rules)

- **Re-resolve the target HWND by title every iteration** (EnumWindows + "微信"/"WeChat" match), never trust a handle stored at session start — app restarts recycle handles, and a stale handle yields a frozen non-updating capture that looks like "no new messages forever". Rebind ONLY sessions whose title marks them as WeChat: mock/test windows must keep their own handle, or a test session gets hijacked onto the real WeChat and replies land in the user's live chat.
- **Raising a window: dispatch on window state.** `IsIconic` → SW_RESTORE; not `IsWindowVisible` (hidden via SW_HIDE) → SW_SHOWNORMAL — **SW_RESTORE cannot un-hide a SW_HIDE'd window**, and using it alone on one produces a permanently frozen capture. Only then SetForegroundWindow. A missing WeChat window should emit a throttled "please open/restore WeChat" warning and skip the step — never a silent freeze.
- **Two capture sources — know which one you are holding.** PrintWindow/PW_RENDERFULLCONTENT reads the window itself (occlusion-immune; blank when minimized). Screen-region BitBlt reads what is physically on screen (fresh pixels; but shows whatever covers the target, and a DPI-unaware process clips monitor edges). Before/after send-verification frames must come from the SAME source — mixing them makes an occlusion moment read as a huge diff (false "sent"). Watch trigger diffing in background mode is PrintWindow on purpose.
- **Before injecting typed text: the target must actually hold foreground** (`GetForegroundWindow() == hwnd`, re-checked right before the paste) and any click point must resolve (WindowFromPoint → top-level) to the target. Skip on failure — with the wrong focus the paste types the customer's reply into whatever app the user is working in and Enter sends it. This outranks send success: a skipped send retries; a mistyped send is an accident in front of the customer.
- **Restoring your OWN window must never activate it.** SW_RESTORE on a MINIMIZED window always brings it to the foreground, and both "official" no-activate paths are unusable for minimized windows — `ShowWindow(SW_SHOWNOACTIVATE)` AND `SetWindowPlacement(showCmd=SW_SHOWNOACTIVATE)` still steal the foreground (verified with a live Tk probe: minimized window + either call → it becomes foreground; only the already-visible case honors NOACTIVATE). The working pattern (`native.window_restore_no_activate`): save `GetForegroundWindow()` → SW_RESTORE → ~50 ms later, if the foreground is now yourself, `SetForegroundWindow(prev)` — the process just called ShowWindow so it holds foreground permission and the give-back succeeds; if the user already clicked elsewhere, do nothing. Every self-restore path must use it — the realtime-monitor endpoint's per-frame `minimize → capture → restore` loop (an activating restore there pops RFlow every frame), `watcher.start`/`stop`, and `_act` completion. In background mode (`pin_wechat=false`) do not minimize or restore ANY window at all (the own-window minimize in `watcher.start` and `_act` is gated on `pin_wechat`): the typing-moment raise of the TARGET is the only sanctioned foreground contact.
