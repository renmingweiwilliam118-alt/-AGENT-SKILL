# Pywebview Desktop Apps on Windows

## When to Use

Building or debugging a pywebview desktop app on Windows (EdgeChromium backend): wiring native file dialogs from web UI, making window controls (min/max/close) work from JS, or calling Win32 common-dialog APIs via ctypes. Also use when a pywebview "save" silently does nothing and you need to find why.

Task class: Python desktop apps using pywebview (EdgeChromium backend) on Windows — making native dialogs and window controls work from web UI, and debugging ctypes Win32 common-dialog calls.

## Always-on rules

1. **`js_api` methods run on worker threads, never the GUI thread.** Never call WinForms dialogs or `window.minimize()/maximize()/close()` from a js_api method — they are GUI-thread-bound and fail silently or raise. What is safe in js_api: file I/O, Win32 PostMessage/ShowWindow via ctypes, and issuing HTTP requests to an in-process backend.
2. **User-initiated "Save as" from JS: use pywebview's built-in download pipeline, not a hand-rolled worker-thread `GetSaveFileNameW`.** Set `webview.settings['ALLOW_DOWNLOADS'] = True` (default is `False` — with the default, every browser download is silently cancelled, which looks like "save does nothing"), then keep the frontend blob `<a download>` fallback in place; the EdgeChromium `on_download_starting` hook shows a native `WinForms.SaveFileDialog` on the GUI thread and rewrites the download path. Details and source locations: `references/pywebview-dialogs.md`. This mechanism is read from pywebview source; when you deploy it, verify in the live app that a real download actually triggers the save dialog before declaring it fixed (the source pipeline can differ between pywebview versions).
3. **Window control:** route it through a thread-safe path — Win32 `FindWindow` + `ShowWindow`/`PostMessage(WM_SYSCOMMAND)` via ctypes, or an HTTP endpoint on the in-process FastAPI/uvicorn backend that the frontend `fetch`es (resilient even when the pywebview JS bridge failed to inject). To find the right HWND of a frameless pywebview window, walk CIM process ancestry (`msedgewebview2.exe` → launcher → python host); never assume by pid.
4. **Verify a native dialog actually appeared — never trust the return code.** `GetSaveFileNameW`/`GetOpenFileNameW` return 0 for both failure and user-cancel; `GetLastError` is unreliable afterwards (observed patterns: `87` = 0x57, the low word of E_INVALIDARG — a COM/INVALIDARG-class failure, NOT user-cancel; `1813` = FNCANCEL, which does mean a dialog opened and was cancelled). Verify by `EnumWindows` watching for class `#32770` (classic dialogs) or `Windows.UI.Core.CoreWindow` (explorer-style) to appear; auto-close probes with `PostMessageW`.
5. **This host: write Python probes to a `.py` file and run it.** Bash heredocs containing `&`/complex expressions get misjudged as backgrounding and the whole terminal command is refused. And when the payload is Python *source* containing string-literal escapes (`\n`, `\\`, f-strings with embedded newlines), do NOT generate it through a `python - <<'EOF'` heredoc: the host's transmission layer mangles the backslash-escapes into real newlines and the f-strings break with `SyntaxError: unterminated f-string`. Author the patch with the `patch`/`write_file` tool instead, and validate with `ast.parse` before running.
6. **The edgechromium JS bridge can arrive AFTER the page's `load` event.** On WebView2, `window.pywebview` injection is not guaranteed at `load`; a frontend that refreshes state once at `load` and early-returns will show stale defaults (KB 0, unset model) that masquerade as data-layer bugs. Boot the UI with a long-poll: poll `window.pywebview && window.pywebview.api` every ~150 ms for up to ~20 s, then refresh; after the budget, keep a low-frequency retry interval so a late bridge still recovers the UI. This is not flakiness — it is normal WebView2 timing. Any state refresh that early-returns on a failed bridge call must be null-safe on the returned payload: a truthy error-shape object (e.g. `{ok:false}`) slips past a bare truthiness guard and makes every later poll abort permanently at the first property access, leaving the UI stuck on defaults. Show the connection state in the UI (a 'backend connected' indicator toggled by the poller) so a bridge problem stays visually distinguishable from a data or design problem.
7. **Page JS that uses `async/await` needs `webview.start(gui="edgechromium")`.** The legacy backend won't execute it; keep a bare `webview.start()` fallback for hosts without WebView2.
8. **Frozen PyInstaller GUI build MUST pass `--noconsole` (=`-w`), or a console box spawns next to the WebView window on every launch.** The default (no flag) is a console-subsystem EXE: `webview.start(gui="edgechromium")` still opens a native window, but Windows also allocates a console, so the user sees a black command box on top of / beside the app and has to close it each time — they will report it as "the app pops a black window." Build: `python -m PyInstaller --onefile --noconsole --add-data "ui;ui" --collect-data pywebview --hidden-import mss app.py` (Windows flag syntax `src;dest`). After build, VERIFY without trusting the flag: read the PE header subsystem — `subsystem = struct.unpack_from('<H', data, pe_off + 24 + 68)` where `pe_off = struct.unpack_from('<I', data, 0x3C)` — value `2` = GUI (no console), `3` = CONSOLE (box will appear). Rebuild if it reads 3. No guard needed in code (no `input()`/`stdin` in the entry), but if the app ever reads stdin, gate it on the frozen check or it will raise on startup in noconsole mode.
9. **Frozen (PyInstaller) build: split asset dir from data dir.** Load bundled resources (the web UI) from `sys._MEIPASS` when frozen; keep user-writable data (config, knowledge base, logs) in the exe's own directory. Resolving the HTML from the exe dir 404s and renders a white UI in the packaged build. Exact flags, the headless screenshot-verification loop, and the live-instance verify-latest-build protocol — incl. process-name liveness probing (deployed file-base name, not `--name`), build-version log markers that outlive log clears, and the stale-instance vs surviving-bug triage: `references/pyinstaller-packaging.md`.
10. **Put the process in Per-Monitor DPI awareness before any screen-coordinate work.** `mss` captures **physical** pixels (it reads a screen DC); `GetSystemMetrics`, `GetCursorPos`, and `CreateWindowExW` return **logical** pixels unless the process is DPI-aware — so a region picked in one space and captured in the other silently drifts by the scaling factor (×1.25/×1.5), which looks exactly like "selection keeps missing". Call `SetProcessDpiAwareness`/`SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` at process start, **before** any window/DC exists (exact ctypes form in `references/region-picker-rubberband.md`), then `mss.monitors[0]` and your Win32 coordinates share one physical space. If you cannot set DPI awareness, convert at every boundary — never assume they match. A one-shot probe where mss width equals `GetSystemMetrics` is NOT proof the app is aligned: the probe's own interpreter may have been started DPI-aware while the app binary is not — always call the awareness API inside the app at startup, before any window/DC, and re-probe within the running app.
11. **When "drag on a scaled-down preview" region selection keeps mis-selecting, switch to a native desktop rubber-band, not more coordinate math.** A drag on a downscaled thumbnail drifts because the mapping depends on `naturalWidth`/scale/origin that change when the preview refreshes mid-drag, and Y-drifts when width and height scaling are conflated. The robust interaction is hide→pick→show on the real desktop: hide the main window, create a full-virtual-screen `WS_EX_LAYERED` topmost overlay, poll `GetCursorPos`/`GetAsyncKeyState` to draw a live rubber-band, read the release point as **real screen coords** (no math), then show the window. Esc cancels; a timeout auto-restores the window. Trigger it from a UI button AND from a global hotkey: register `RegisterHotKey(None, id, MOD_CTRL|MOD_ALT, 'R')` in a dedicated message-pump thread (the main GUI thread is owned by `webview.start()`, so the hotkey must be pumped elsewhere). The picker must also **pause background native loops while it runs** (rule 19) — otherwise the monitor's screenshot grabs race the picker's window churn and crash the interpreter after the pick "succeeds". **If layered transparency is disabled on the host (error 87) or the solid-window fallback crashes the packaged build on teardown, do not keep patching window classes — drop to pure global mouse tracking (`GetAsyncKeyState` + `GetCursorPos`, zero window creation), which has no crash surface at all, and surface the selected rect only in the app's preview.** A user who says "don't darken the desktop, just show the box" or "the screen goes black when I click select" wants tier 4 directly, not a re-tuned dimming overlay. Full escalation table (layered → solid-window → pure-tracking, with the exact dimming-on-mousedown cause of the black screen), the recipe (two static layered windows or `UpdateLayeredWindow`, GDI premultiplied-alpha colors, 64-bit ctypes restypes, `WINFUNCTYPE` window class, per-thread message pumping, DPI alignment, hotkey loop): `references/region-picker-rubberband.md`.
12. **Exit-clean picker + 64-bit handle gotchas: see `ctypes-win32-windows`.** The `WINFUNCTYPE` window class + per-thread message-pumping pattern above can leave a C trampoline that the main thread's GC reclaims at exit → `RC 0xC0000005`. If the app must exit clean (and layered APIs return error 87, forcing the solid-window fallback), register the class on the main thread with `lpfnWndProc` = the **bare address of `user32.DefWindowProcW`** and run each pick in a **transient `join`ed thread** — confirmed `RC 0` with no trampoline in the GC pool. Also: on x64, every ctypes call that **returns or consumes a handle/pointer** (HGLOBAL/HBITMAP/HWND/HDC, `GlobalAlloc`/`GlobalLock`/`GlobalFree`, `CreateWindowExW`, `SetClipboardData`, …) needs explicit `restype`/`argtypes` (`c_void_p`/`c_long`); without them a large 64-bit handle is coerced to a 32-bit int and the call raises `OverflowError: int too long to convert` — this is the classic silent killer of a clipboard text-send path in an x64 pywebview app. Concrete rules: `ctypes-win32-windows` SKILL.md rules 2, 6, 8, 9.
13. **When a monitoring loop floods one repeated log line, fix the loop's upstream channel before touching the loop.** A "每轮都被跳过/上一轮未完" spam is usually a symptom: the worker it queues on is blocked in an LLM rate-limit backoff (429 → `Retry-After` sleep of 10s–40s), so every later cycle sees the busy flag set and skips. Read the last successful log line to find which model actually answers — the *default* configured model may be an exhausted free tier while a different model is what worked before — and fix the default, not the loop. Two companion rules that follow: (a) throttle the skip log so it reports at the Nth occurrence, not every cycle (the user reads a flooded log as "stuck", which buries the real cause); (b) a **manual** user action ("立即识别") must bounded-wait on the shared busy flag (~10 s) instead of hard-rejecting on the first check — a click means the user is willing to wait a beat, and a hard rejection reads as the button being broken.
14. **After a live drag, never re-render the canvas that hosts the preview in the same event.** Dragging a selection box over a preview image draws a transient rect that only exists in the DOM; calling the "refresh preview" routine from the mouseup/save handler repaints the image underneath and erases the box, so the user sees nothing until the *next* interaction — they report it as "the preview only appears after I release." Keep the transient visual until the next genuine refresh trigger (the backend push, an explicit refresh button), and let the save handler only persist state. Model-availability triage behind a persistent "识别/执行失败" report (404 wrong-id vs 404 no-credits, reasoning models whose answer lands in `reasoning` not `content`, hourly-expiring OAuth tokens, transient 5xx to retry rather than debug, and the vision-reads/agent-writes split that stops one-sentence replies): `references/llm-endpoint-integration.md`. Document-ingest knowledge bases (upload Excel/Word/PDF → parse → `.md` → token-split fuzzy retrieval, and why exact-substring retrieval is the real bug): `references/knowledge-base-ingest.md`.

19b. **Never let the vision model write the reply — it caps the reply at one sentence.** When one model both reads the screenshot and drafts the answer, its prompt naturally asks for a "一句简短" draft and the persona/knowledge-base only ever trims that string, so the user gets a one-liner with no persona. Split it: the vision model extracts messages + input-box position and is told explicitly not to write a reply; a second, always-run composer call (persona + tone + banned words + knowledge base + conversation) writes the full reply — `max_tokens` ≈ 400, `temperature` ≈ 0.5, instructed to be complete and paragraph-natural, never a one-liner. Don't gate the composer on a knowledge-base hit (a user with no KB would fall back to the vision one-liner). Details and the 5xx-retry rule: `references/llm-endpoint-integration.md`.

19c. **Latency fast path (measured ~50% saving): once the composer prompt is correct, it is safe to FOLD the draft back into the vision call.** The two-call split of 19b costs a full second LLM round trip per recognition. With a strong multimodal model you can instead ask the vision call to return a `draft` field in the same JSON (read messages + write reply in one call) — provided the prompt carries an explicit length instruction, otherwise the model collapses back to a one-liner. Drive the length from one agent config key (`reply_len`: `short`→"一两句话说清，不超过 60 字" + `max_tokens=120`; `medium`→"100 字左右" + 300; `long`→"分点讲全，200~300 字" + 500) and apply the SAME hint and cap in both the vision prompt and the composer, so the fallback path produces the same length. Log which path ran ("快路径：vision 一次调用直接生成草稿 N 字") so latency complaints are diagnosable. Keep the composer call as the fallback whenever `draft` is empty — it is the only path that has the knowledge base and the full conversation memory, so quality-sensitive flows (multi-turn context, KB answers) should prefer it.

15. **On OneDrive machines the real Desktop is `%USERPROFILE%\OneDrive\Desktop`; `%USERPROFILE%\Desktop` is a decoy that accepts writes but the user never sees.** Deploying an exe "to the desktop" into the plain path means every fix lands where the user never looks — they keep double-clicking the OLD exe in OneDrive and re-report every already-fixed bug as still present, and the version marker you check will never match what you deployed. Resolve the true path with `[Environment]::GetFolderPath('Desktop')`, and whenever a user re-reports a bug you already fixed, verify the RUNNING process's `ExecutablePath` (via `Get-CimInstance Win32_Process`) against the file you deployed before touching code: different path ⇒ wrong deployment folder, full stop. Also delete superseded copies (old app names) from the same folder so a stale binary cannot be launched by habit.

21. **Every subprocess a GUI app spawns needs `creationflags=subprocess.CREATE_NO_WINDOW`, not just the long-lived ones.** `--noconsole` (rule 8) suppresses the app's OWN console; it does nothing for child processes. A per-operation helper (`subprocess.run([exe, "call", …])`) without the flag makes Windows allocate a console for each invocation, so the user sees a black command box flash on every action — reported as "一直弹命令框". The trap is asymmetry: the daemon-launch `Popen` gets the flag (it's the one you think about) while the hot-path `run` calls don't. Define one module constant `_NOWIN = getattr(subprocess, "CREATE_NO_WINDOW", 0)` and pass `creationflags=_NOWIN` to **every** `subprocess.run`/`Popen`/`check_output` in the app. On non-Windows the constant is 0 and harmless.

16. **Synthetic clicks land nowhere unless you activate the target window first, and vision-model coordinates must be clamped, not rejected.** A pick/execute flow whose log says "已填入输入框" while the target app (WeChat etc.) shows nothing is almost always focus, not coordinates: `SetCursorPos` + `SendInput` click does not change foreground focus, so the keystrokes go to the pywebview window. Before clicking: `WindowFromPoint(x,y)` → `GetAncestor(hwnd, GA_ROOT=2)` → `ShowWindow(top, SW_SHOW=5)` → `SetForegroundWindow(top)` → `SetFocus(top)`, then click (double-click for inputs that need a caret). **Run the whole activation + click + paste sequence under the one global native lock (rule 17)** — calling `SetForegroundWindow` from a js_api worker thread while the GUI thread runs ctypes is a confirmed trigger of the `0xC0000005` AV; when in doubt, skip the activation API and use a physical double-click, which lets the target window take focus itself. And a vision model's estimated `input_box` pixel coordinates are routinely wrong or full-screen-valued — never gate the execute on them being in range (a rejection reads as "the button is broken"): normalize oversized values modulo the region size, then clamp with a ~4% safety margin, so every recognition yields a clickable point. Telling the model the screenshot's real pixel dimensions in the prompt makes its coordinates far more accurate. Recipe: `references/region-picker-rubberband.md`.

17. **Serialize EVERY native call behind ONE global lock — concurrent ctypes/mss from multiple threads crashes `python314.dll` with `0xC0000005`.** A pywebview app with background workers (monitor loop, recognition, injection) plus the GUI thread all touching ctypes/mss gets an access violation inside `python314.dll` at random points — typically the moment a user action fires a screenshot grab and a key-mouse injection at once (a "click 立即识别 → app instantly exits" report). This is NOT the trampoline-GC teardown of rule 12 (that fix alone does not stop it) and it is not a bad coordinate: it is a data race on the interpreter's native-call machinery. Create one module-scope `threading.Lock` and wrap every function that enters user32/kernel32/mss — `grab_png`, `virtual_screen`, `grab_thumb`, `win32_click`, `win32_send_text`, `win32_enter`, `SetForegroundWindow`, clipboard ops — with it, so exactly one thread is ever inside native code. Diagnose a crash like this from the Windows event log before theorizing: `Get-WinEvent -FilterHashtable @{LogName='Application'; Id=1000; StartTime=(Get-Date).AddHours(-2)}` — read the **faulting module** (python314.dll + exception 0xc0000005 = native-call race, not your Python code) and cross-check the timestamp against your last log line to find which user action triggered it. Note the crash signature repeats across builds at different offsets; that pattern (same module, different offsets, multiple timestamps) is the race, not a fresh regression.

18. **Bare `uiautomation` is dead on WeChat 4.0.5+ (Qt Quick renders an empty shell), but `cua-driver`'s UIA walk reads the full 161-element tree — input box, session list, message list — and a token-based `set_value` + `hotkey[enter]` send is VERIFIED working end-to-end on 4.1.15.** WeChat migrated from Qt Widgets (each control = an HWND) to Qt Quick/QML (OpenGL canvas, no per-control HWND), so `uiautomation` sees exactly one near-empty `PaneControl`. Probe before believing: `uiautomation.WindowControl(ClassName="Qt51514QWindowIcon")` then walk the tree — if total accessible nodes ≤ 2, the app is Qt Quick and bare UIA is dead. The same applies to any app showing class `Qt51514QWindow*`. **Do not generalize that result to every UIA client**: on the same machine, same minute, bare `uiautomation` read 51 nodes with no input box while cua-driver read 161 including the input. Three clean escalation tiers below it: (a) **force software rendering** — set `QT_ANGLE_PLATFORM=software` + `QT_OPENGL=software` env vars before launching, or set compatibility to "System" DPI — Qt falls back to QWidget mode and the control tree reappears; (b) **activate the Qt accessibility gate** — measured working on WeChat 4.1.15 via `wechatauto-replica` (writes a gate byte in `Weixin.dll`, tree goes 1 → ~45 real controls, window class becomes `mmui::MainWindow`) — but with THAT tool no standard `EditControl` for the chat input appears (custom-painted input; its RVA table is pinned to 4.1.12 while the user ran 4.1.15); (c) **DLL injection / protocol hook** (e.g. WeChatFerry) — most powerful but gray-area, version-pinned, ban-risk. Tier (b) also needs `winsdk` (requires Visual Studio to build) for its auto-open-chat, so its OCR fallback channel is often unavailable. **Before writing any UIA code, run `scripts/wechat_cua_probe.py probe` — it bootstraps the daemon, dumps the tree, and reports whether the input/session/message controls are addressable.** For READING messages, `wechatauto-replica`'s SQLCipher local-DB decryption is version-insensitive and strictly better than screenshot-OCR (exact text, full history, no per-frame vision). For SENDING, if the user has a WeCom (企业微信) `corpid`+secret, the official HTTP API beats every GUI tier. **To embed this into a shipping app**: bridge module (`WeChatCua` class with `connect/open_session/send/verify_sent/read_messages`), cua-first + legacy fallback in the send layer (`send_engine` config key), PyInstaller `--add-binary` for both exes, and a synchronous test of the bridge function (the async thread wrapper hides failures). Full integration pattern: `references/wechat-automation.md` §"Embedding cua-driver into a desktop app".

19. **A modal native operation must pause background native loops — a mode flag alone is NOT enough; stop the thread.** A region picker creates and destroys real Win32 windows for its whole duration, and that window churn runs outside the app's native lock, while the monitor loop keeps calling `grab_png` every few seconds. The crash lands *after* the pick completes — `set_region` + the thumbnail refresh + the next monitor tick fire at once — as `python314.dll 0xC0000005`, which the user reports as "clicking 桌面圈选 instantly kills the app". The tell: the log shows a successful pick seconds before the crash. **Measured**: setting a `core.picking` flag that the monitor loop checks before its grab is insufficient — the monitor can already be *inside* `grab_png` when the flag flips (the crash recurred ~14 minutes after the flag was added). The robust sequence is: record `_was_monitoring`, call `stop_monitor()`, sleep ~0.2 s so the thread exits its current grab, run the pick, then `start_monitor()` again if it was running. Keep the flag as belt-and-braces (the loop still `continue`s past its grab while set), but never rely on it alone. Diagnose by cross-checking the event-log crash timestamp (`Get-WinEvent … Id=1000`, rule 17) against the last app log line.

20. **When a drag on a scaled-down preview must remain, map coordinates in exactly one function per direction and apply the thumbnail scale exactly once.** The bug behind "the box I drag doesn't match where it lands" is the scale factor applied at two or three layers — a `thumbPos` returning *thumbnail* pixels that the drag handler then multiplies by `inv`, while the overlay rect is positioned with yet another factor — compounded by using one `sc` for both axes on a non-square image (Y drifts, X doesn't). Write `thumbPos(e)` to return **screen pixels in a single step** (mouse position as a 0–1 ratio of the image box × natural size × `inv` + virtual-screen origin `ox/oy`), and `screenToCss(sx, sy)` for the reverse (screen → minus origin → ÷ `inv` → × CSS scale); the mousemove/mouseup handlers then do pure screen-pixel math and never touch `inv` again. Freeze `inv/ox/oy` at mousedown so a mid-drag preview refresh cannot shift the mapping, and size the overlay rect through the same reverse function rather than a separate width formula.

22. **When a user re-reports a bug you already fixed, before touching code again, verify the build artifact is actually fresh — check the output file's timestamp, not the build script's exit code.** A build script that wraps `python -m PyInstaller …` and reports `rc=0` can still have produced nothing: PyInstaller may not be installed in the exact Python interpreter the script invokes, so the build fails silently and the script copies the previous binary. The symptom is a user saying "it's still broken / still black / still crashing" after several rounds of confident fixes — the exe on disk never changed. After EVERY build, run `ls -l dist/yourapp.exe` and confirm the timestamp is minutes-old, not hours or days. If stale, the build silently failed: check `python -m pip show pyinstaller` in the exact interpreter the build script uses, install if missing (`python -m pip install pyinstaller`), delete the old `dist/` output to force a clean rebuild, then re-verify the timestamp. Never copy a stale binary to the user's delivery path and call it "fixed."

23. **When a fix "doesn't take effect" despite clean deploy and fresh build, grep for duplicate function definitions before theorizing about anything else.** Python silently uses the LAST definition of a function name in a module; any earlier patched version is completely shadowed. This is especially insidious after iterative refactoring where a function is replaced in place but a stale copy remains lower in the file — the patch tool reports success, `py_compile` passes, the build succeeds, yet the running code is the OLD definition. Before debugging deployment paths or caches, run `grep -c "^def funcname(" file.py`; a count > 1 is the bug. Delete every duplicate, keeping only the intended definition. **Rules 22 and 23 stack — check both independently and do not stop at the first one you find.** A session that shipped three "fixes" the user kept rejecting had BOTH faults live at once: the build script's interpreter lacked PyInstaller (rule 22, so `dist/` never changed) AND a second `def _rubber_band` shadowed the patched one (rule 23). Finding only the timestamp bug and rebuilding would still have shipped the old function. The mechanical order when the user says "it's still the old behavior": (a) `ls -l dist/…exe` timestamp is minutes-old; (b) `grep -c "^def <the function you patched>("` is 1; (c) only then read code logic. State the result of (a) and (b) to the user explicitly — "wrong deployed file / old exe / shadowed function" are all they need to hear, and each maps to a different fix.

24. **For an auto-reply loop, dedup on a persistent full-text "already replied" set — never on a truncating key or a rolling window.** "同一条消息被重复回复了两三次" almost always comes from one of two cheap dedup shortcuts: (a) the key is only the first N characters of the message (`text[:24]`), so two different customer messages that share an opening clause ("我想咨询一下关于…") collide and the second is dropped — the user sees the agent ignoring the new question and repeating the old answer; (b) dedup is recomputed from a rolling conversation window (`_conv[-15:]`), so once a message scrolls out of the window it looks new again and gets a second reply. Fix: keep a dedicated `self._replied` set keyed on the **whole message with whitespace stripped**, add the key the moment a message is merged for reply (before the send, so a re-read of the same screen in the same cycle cannot double-reply), never remove on success, cap it (~500 entries, drop oldest), and keep a full-text membership check as a tiebreaker when the truncated key collides. Mark at merge time rather than after a successful send: gating on send success lets a failed send re-enter the loop, but it also means a send that succeeded while the log failed to record will re-send — for customer-facing auto-reply, under-replying is always the safer failure. Widening the `_conv` window and lengthening the prefix are both false fixes; the persistent set is the actual fix. Verify with the three cases that map to the two symptoms: same message repeated across cycles (added == 1 only the first cycle), two distinct messages sharing a 24-char prefix (both added), and a message re-appearing after 60 other messages scrolled past (added == 0).

25. **Let the user write the reply prompt itself, and when they do, let it replace the whole template.** Two agent fields that look redundant to a user ("人设描述" vs "自定义回复指令") differ by scope: the persona field is ONE line inside a program-built template the user cannot see; the custom-prompt field, when non-empty, becomes the entire system prompt, and the persona/tone/length fields are ignored. Ship it that way and say so in the UI, otherwise the user fills in both and cannot tell which one won. Mechanics: a `custom_prompt` agent key (default `""`); a `.format(**fields)` substitution so the user can drop `{role} {tone} {persona} {banned} {greeting} {convo} {context} {kb}` placeholders into plain Chinese prose (wrap in `except (KeyError, IndexError, ValueError)` so a typo'd placeholder degrades to the raw string instead of raising); apply the SAME override in the fast path (the vision call) by replacing the persona header but KEEPING the JSON output contract, or the fast path silently reverts to the default template and the user's instruction only works half the time. Keep the `reply_len` → `max_tokens` mapping active on both paths. And when the user asks "这些 {tone} {convo} 都啥意思啊": answer in one plain-language table (placeholder → what it becomes → where that value comes from) plus a copy-paste Chinese example, and state up front that the placeholders are optional — "正常输入中文就可以" is what they are actually asking. Use `ctypes.cast(ctypes.pointer(buf), wintypes.LPCWSTR)`; plain Python `str` auto-converts fine for short fields. Keep every buffer alive for the whole modal call.
- Set `restype = wintypes.BOOL` before the call; pass the struct via `ctypes.byref`.
- `nFile` is the buffer CAPACITY in characters, not the current length.
- `lpstrInitialDir`: backslash Windows paths only — mixed `/` separators can trip parameter validation.
- `OFN_EXPLORER` (0x2) switches the call to IFileDialog, which needs STA COM on the calling thread; worker threads that never called `CoInitializeEx` can fail this path even when the classic path works. If it fails on a worker thread, drop the flag or use rule 2 above — do not keep debugging the struct.
