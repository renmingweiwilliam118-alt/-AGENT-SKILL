# Tauri + PyInstaller standalone desktop packaging

## When to Use
- Packaging a Python (FastAPI/uvicorn) web app as a native double-click desktop binary
- When the deliverable must run on machines with no Python/Node installed
- Wrapping a browser-automation backend that must reuse the user's system browser

Goal: end user copies one folder, double-clicks one .exe, it works. No Python/Node/uv on the target machine. Architecture: Tauri 2 shell (native exe) spawns the PyInstaller-frozen backend, then opens a webview at `http://127.0.0.1:<port>/` — same-origin, so `/api` and `/ws` resolve with zero CORS. The backend is dual-role (one frozen exe acts as UI server AND worker, e.g. a crawler, selected by an env var `MEDIA_CRAWLER_ROLE=server|crawler`; the server role re-spawns itself with the worker role). Use CDP mode for browser automation (drive the user's system Chrome/Edge instead of bundling a ~150MB Playwright browser). Pin Tauri 2.x (stable) — Tauri 3 is alpha.

## Procedure
1. Decouple backend startup into a launcher entrypoint that (a) resolves the interpreter/command, (b) picks a free port, (c) writes the port to a READY FILE (env-pointed) plus prints a ready line for dev, (d) runs the server.
2. Tauri shell (`desktop/src/main.rs`):
   - Spawn the backend with stdout+stderr redirected to a LOG FILE and the ready-file env var set. NEVER pipe stdout: the moment the pipe reader dies (window close, kill during test), every Python `print()` raises OSError and takes the whole backend down.
   - Poll the ready file (~150ms interval, ~120s timeout) for the port.
   - Open the WebviewWindow at `http://127.0.0.1:port/`; kill the child on window destroy. Hold the child in a `static OnceLock<Mutex<Option<Child>>>` so the 'static event closure can reach it without borrow conflicts.
   - Zero-config UX: auto-locate the bundled backend next to the shell exe (`current_exe()` dir → `Backend/Backend.exe` or `Backend.exe`) and use it with no env vars; fall back to a dev command only when absent.
3. Make the backend frozen-safe: resource paths via `sys._MEIPASS` when `sys.frozen` (static frontend dir, config/data files). The frontend is snapshotted into the bundle at package time — rebuild the webui first if it was re-skinned.
4. PyInstaller: onedir, not onefile (onedir is far more reliable for heavy dep trees). `--hidden-import` every dynamically-imported module (per-platform worker modules), `--collect-all` for hard-to-freeze libs (playwright, cv2, matplotlib, pandas), `--add-data` for config/lib/constant dirs AND the built frontend (built dir → `webui` under `_internal`).
5. Assemble the deliverable: `App.exe` (shell) + `Backend/` (onedir tree) + a plain-language 使用说明.txt for non-technical users (double-click → pick → scan login → where data lands → the one hard requirement, e.g. a system browser). Zip it.
6. Verify as the end user: launch the shell with ZERO env vars; poll the ready file; health-check the port; GET `/` and confirm the right index.html is served; confirm asset bytes exist on disk inside `_internal`; confirm root-level static files the frontend references (favicon, logo images) return 200, not 404.
7. When adding a Tauri native command (file dialog, export, etc.): Tauri 2 injects the `AppHandle` as the first command parameter — `AppHandle::try_current()` does not exist in Tauri 2 and will not compile. `withGlobalTauri` is a key under the `app` section of `tauri.conf.json` (enables `window.__TAURI__.invoke` in the webview), NOT a Cargo feature — adding `features = ["with-global-tauri"]` to the tauri crate fails the build. Frontend calls use camelCase args (`invoke('export_data_file', { filePath })` ↔ Rust `file_path`). Before writing any code against a tauri-plugin-* API, read the exact version's source (`references/tauri-native-commands.md` has the verification recipe and the dialog 2.x shapes) — method names differ across plugin major versions and guessing costs a full recompile cycle each time.

## Pitfalls
- uv-managed venvs have no pip: install tooling with `uv pip install pyinstaller`, never `python -m pip`.
- Run the freeze script with the project's venv interpreter (`.venv/Scripts/python.exe build_desktop_backend.py`), never bare `python` — and launch it through the terminal tool, not the execute_code kernel: the kernel's managed runtime site-packages can shadow the project's (e.g. a broken PIL breaks PyInstaller's matplotlib hook and aborts the freeze mid-run). — a system interpreter without the project deps silently produces a backend that crashes on launch (`No module named 'uvicorn'`), and the bug only surfaces when the user double-clicks. After each freeze, confirm `uvicorn`/`fastapi`/`starlette` byte markers exist inside the frozen backend exe (they live in the embedded archive; `_internal` dirs may legitimately not list them) before assembling the deliverable.
- After the re-build loop, verify the fix actually compiled in before telling the user it's fixed: byte-check the shell .exe for the new markers (e.g. the capability whitelist string `http://127.0.0.1:*`, or a new command name) and launch the assembled folder to poll the ready file. Source edits to capabilities or main.rs are invisible to the running app until this whole loop completes — skipping the check is how "still not working" reports recur. Marker bytes can be absent even in a correct release build (LTO string dedup): a byte-check miss is inconclusive, not a failed build — when the byte check is inconclusive, launch the assembled folder and probe behavior (endpoint responses, served bundle) instead.
- Any backend or webui fix requires the full re-freeze loop (PyInstaller rebuild → reassemble folder → rezip → recopy to the delivery location); the stale frozen exe silently ships the old bug. A capability (`remote.urls`) or `main.rs` change is the same kind of shell-side fix — it ships in the shell .exe, so re-run the whole loop and don't assume the old .exe still works.
- Webview at a DYNAMIC/external origin (free-port backend): Tauri 2 silently DROPS `invoke` from any origin not in the capability's `remote.urls` — the export/save-dialog Promise just never settles ("button does nothing"), with no error. `withGlobalTauri: true` does NOT cover this; it only whitelists the same-origin `tauri://` case. Add `remote.urls` (wildcard `http://127.0.0.1:*` or a pinned port) + the plugin permission (e.g. `dialog:default`) to the capability, and add a trivial `desktop_ping` self-test so a dead bridge surfaces instead of silently dying. See `references/tauri-native-commands.md` "Dynamic / external webview origin".
- MSYS/git-bash curl against 127.0.0.1 flakily returns 000/0B even when the server is up — verify with PowerShell `Invoke-WebRequest` or by checking files on disk.
- `taskkill` through git-bash takes single-slash args (`/F /PID`); double-slash mangles them.
- Multi-byte emoji/CJK greps in bash are unreliable — byte-level checks in Python.
- When a UI report says "I don't see my files/data," audit the backend file-listing extension allowlist against the crawler's ACTUAL default output format before touching the frontend — an allowlist like `{.json,.csv,.xlsx,.xls}` silently excludes `.jsonl` (the default output of most crawlers), so the file browser shows nothing even though files exist on disk. Fix the listing, record-count, preview, and stats endpoints as one chain.
- CWD-relative data-dir resolution is the mirror image of the `_MEIPASS` trap: `Path(__file__).parents[2] / "data"` is correct in the source tree but points inside `_internal` once frozen — under `sys.frozen`, resolve from CWD (which the shell sets to the app folder) or an env var instead.
- Path strings crossing the API→Rust boundary: backslash-separated relative paths (`a\b\c.jsonl`) must be normalized to forward slashes before `Path::join` on Windows, or segments stick together.
- End-user affordance rule: never hide primary actions behind hover-only reveal (`opacity-0 group-hover:opacity-100`) — non-technical users don't hover to discover; keep action buttons on data/file cards always visible.
- "Check the environment" endpoints (e.g. `/api/env/check`) must short-circuit in frozen mode: the bundled exe has no source-tree `main.py` to probe, and `_resolve_python()` returns a command-prefix LIST plus an env dict, not a single path string — treat it as a list or you get `TypeError: expected str, bytes or os.PathLike, not list`. Guard with `getattr(sys, "frozen", False)`.
- A FastAPI server that serves the frozen webui must mount the webui ROOT, not just its subdirectories: with only `StaticFiles` mounts for `/assets`-style subdirs, root-level files the frontend references (`/favicon.ico`, logo pngs) 404. Add `app.mount("/", StaticFiles(directory=WEBUI_DIR, html=True))` as the LAST mount — routes registered earlier win, and unknown paths fall back to index.html (SPA behavior). Mount code lives in api/main.py, so it ships only with a re-frozen backend exe: re-freeze after any such fix.
- Changing the app icon is a shell-side change baked into the .exe at cargo build: regenerate `desktop/icons/icon.ico` (multi-size PNG-embedded ICO — newer Pillow changed its `save(format='ICO', sizes=[...])` API, so hand-write the container: 6-byte header, per-entry directory records, embedded PNG blobs) plus PNG variants, update `bundle.icon` in `tauri.conf.json`, and re-run the full loop. Web-side logo: put the PNG in the webui public dir, reference it from index.html (favicon) and the app's header/sidebar.
- After a full visual redesign, users may report "the UI looks exactly the same" — the webview can keep serving a stale/cached bundle. Add `<meta http-equiv="Cache-Control" content="no-cache, no-store, must-revalidate">` to index.html, and before re-zipping confirm the served JS bundle hash matches a fresh `vite build` (byte-check the bundle for a string introduced by the redesign) so the delivery actually contains the new look.
